# ADR 0003: Стратегія контейнеризації, вибір базових образів та ізоляція мереж

* **Статус:** Accepted
* **Дата:** 2026-11-22
* **Контекст:** Лабораторна робота №2 (Контейнеризація порталу StudShare)

## Контекст
Для переходу від архітектурної моделі C4 Container View до відтворюваного локального середовища необхідно упакувати Frontend, Backend API та PostgreSQL у Docker-контейнери з дотриманням принципів 12-Factor App та базових практик безпеки DevSecOps. Потрібно обрати базові образи для runtime-середовища та визначити топологію мереж у Docker Compose.

## Рішення
1. **Базові образи на основі Alpine Linux та Multi-stage builds:**
   * Для Backend API обрано `node:20-alpine` із багатоетапною збіркою: компіляція TypeScript і встановлення dev-залежностей відбуваються на етапі `builder`, а у фінальний образ копіюються лише `dist/` і production-залежності.
   * Для Frontend обрано `node:20-alpine` для збірки Vite та `nginxinc/nginx-unprivileged:1.27-alpine` для роздачі статики та проксіювання `/api/`.
   * Для бази даних обрано `postgres:16-alpine`.
2. **Принцип найменших привілеїв (Non-root):**
   * Усі власні сервіси запускаються від непривілейованих користувачів (`node` у Backend, `nginx`/UID `101` у Frontend).
3. **Сегментація мереж:**
   * Створено дві ізольовані bridge-мережі: `frontend-net` (для `frontend` та `backend`) і `backend-net` із параметром `internal: true` (для `backend` та `db`).
   * Контейнер `db` не публікує порти на хост-машину і фізично недоступний із `frontend` або ззовні.
4. **Керований порядок запуску:**
   * Налаштовано `healthcheck` для всіх трьох сервісів та залежності `depends_on` із умовою `condition: service_healthy`.

## Розглянуті альтернативи
* **`debian-slim` (`node:20-slim`):** має кращу сумісність із нативними C/C++ бібліотеками (`glibc`), проте створює більший розмір образу та ширшу поверхню атаки порівняно з Alpine.
* **`distroless`:** забезпечує максимальну безпеку (відсутність shell та пакетного менеджера), але ускладнює локальне налагодження та налаштування простих healthcheck-команд на етапі розробки.
* **Єдина мережа Docker Compose за замовчуванням:** простіша у налаштуванні, але порушує принцип ізоляції, дозволяючи скомпрометованому Frontend-контейнеру звертатися напряму до порту БД.

## Наслідки
### Позитивні
* Мінімальний розмір фінальних образів (десятки мегабайт замість сотень) та швидке розгортання.
* Захист бази даних від прямого доступу ззовні та з рівня презентації.
* Відсутність стану перегонів (race conditions) під час старту Backend до повної ініціалізації PostgreSQL.
* Повна відповідність вимогам 12-Factor App (конфігурація через `.env`, збереження стану в іменованому volume `pg_data`, graceful shutdown на `SIGTERM`).

### Негативні та компроміси
* Alpine використовує `musl libc` замість `glibc`: у разі додавання у майбутньому важких нативних npm-пакетів може знадобитися перехід на `node:20-slim`.
* Для прямого підключення до БД локальним GUI-клієнтом (наприклад, DBeaver) розробнику доведеться тимчасово використовувати `docker-compose.override.yml`.
