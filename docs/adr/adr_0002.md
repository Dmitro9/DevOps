# ADR-0002: Вибір архітектурного стилю (Модульний моноліт + Асинхронний воркер) та контейнеризації

* **Status:** Accepted (Прийнято)
* **Date:** 2026-11-18
* **Authors:** Команда розробки та DevOps проєкту StudShare

---

## Context (Контекст і проблема)
Команда проєкту **StudShare** має обмежений час на випуск MVP (Minimum Viable Product), але система повинна відповідати жорстким нефункціональним вимогам:
1. Витримувати різкі стрибки трафіку під час екзаменаційних сесій (Scalability).
2. Гарантувати безпеку файлів: кожен завантажений студентом архів лабораторної роботи (ZIP) або документ (PDF/DOCX) має проходити антивірусну перевірку та генерацію прев'ю без блокування інтерфейсу користувача.
3. Підтримувати сучасні практики DevOps: автоматизоване CI/CD, контейнеризацію та observability з першого дня.

Побудова повноцінної мікросервісної архітектури (де кожен домен — авторизація, коментарі, предмети, файли — є окремим мікросервісом) на старті створить надмірні накладні витрати на підтримку мережевої взаємодії, розподіленого трейсингу та деплойменту.

---

## Decision (Рішення)
Ми вирішили застосувати архітектуру **Контейнеризованого модульного моноліту з виділеним асинхронним воркером**, розгорнуту в **Kubernetes**:

1. **Фронтенд:** Single-Page Application на базі **React + TypeScript**, що збирається в статичні файли та роздається через контейнер Nginx.
2. **Бекенд (Core API):** Модульний моноліт на базі **Node.js (NestJS / TypeScript)**. Чіткий поділ на внутрішні модулі (`AuthModule`, `CatalogModule`, `MaterialsModule`, `RatingModule`) дозволяє зберігати простоту розробки в одному репозиторії, але при потребі легко винести будь-який модуль в окремий сервіс у майбутньому.
3. **Асинхронна обробка (File Processing Worker):** Ресурсоємні операції (сканування файлів антивірусом **ClamAV**, розпаковка метаданих архівів, рендеринг першої сторінки PDF для прев'ю) винесені в окремий контейнер-воркер. Взаємодія між Core API та Worker відбувається асинхронно через чергу повідомлень **Redis (BullMQ)**.
4. **Інфраструктура та DevOps:** Усі компоненти пакуються в **Docker-образи**, оркеструються через **Kubernetes** та моніторяться стеком **Prometheus + Grafana + Loki**.

---

## Consequences (Наслідки)

### Позитивні наслідки:
* **Незалежне масштабування читання та важкої обробки:** Якщо під час сесії тисячі студентів лише читають і скачують конспекти, Kubernetes масштабує лише легкі pod'и `Core API`. Якщо наприкінці семестру студенти масово завантажують важкі архіви лабораторних робіт, масштабуються pod'и `File Processing Worker` без впливу на швидкість роботи сайту.
* **Швидкість розробки та простота CI/CD:** Єдина кодова база TypeScript для фронтенду, API та воркера спрощує налаштування пайплайнів GitHub Actions, тестування та Code Review.
* **Висока безпека:** Жоден файл не стає публічно доступним для скачування іншими студентами, доки асинхронний воркер із ClamAV не переведе його статус у стан `VERIFIED`.

### Негативні наслідки та компроміси (Trade-offs):
* **Споживання оперативної пам'яті ClamAV:** Антивірусна база ClamAV потребує близько $1\text{--}1.2\text{ ГБ RAM}$ для роботи у пам'яті. *Вирішення:* запуск ClamAV як окремого сервісу або sidecar-контейнера лише у вузлах воркера з чітко заданими `resources.limits` у маніфестах Kubernetes.
* **Eventual Consistency (Кінцева узгодженість) при публікації:** Після натискання кнопки «Опублікувати лабораторну» файл з'являється у загальному пошуку не миттєво, а через $3\text{--}10$ секунд (після завершення роботи воркера). *Вирішення:* відображення статусу «Файл перевіряється на віруси...» в особистому кабінеті автора та надсилання push/Telegram-сповіщення після завершення.
