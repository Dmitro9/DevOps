# ADR-0005: Впровадження Infrastructure as Code (Terraform) та Configuration Management (Ansible) у хмарі Azure

- **Статус:** Прийнято
- **Дата:** 2026-11-25
- **Контекст проєкту:** StudShare

## 1. Контекст і проблема
Для розгортання та супроводу інфраструктури вебзастосунку **StudShare** у хмарному середовищі необхідний відтворюваний, версіонований та автоматизований підхід. Ручне створення віртуальних машин і конфігурування серверного середовища через вебпортал призводить до дрейфу конфігурацій, людських помилок і неможливості швидко відновити інфраструктуру.

## 2. Розглянуті рішення та вибір

### 2.1. Вибір хмарного провайдера та параметрів обчислень
- **Провайдер:** **Microsoft Azure** (підписка *Azure for Students*).
- **Регіон:** `denmarkeast` — обрано зі списку дозволених політикою підписки регіонів (`francecentral`, `polandcentral`, `norwayeast`, `germanywestcentral`, `denmarkeast`) через наявність вільних обчислювальних потужностей без помилок `SkuNotAvailable`.
- **Конфігурація VM:** `Standard_B2als_v2` (2 vCPU, 4 ГБ RAM, x64) під керуванням **Ubuntu 22.04 LTS** з автентифікацією виключно за SSH-ключем формату **RSA**.

### 2.2. Розподіл відповідальності між Terraform та Ansible
Інструменти розділено за принципом єдиної відповідальності:
- **Terraform (Infrastructure Provisioning):** декларативно описує та створює базові хмарні ресурси (`azurerm_resource_group`, `azurerm_virtual_network`, `azurerm_subnet`, `azurerm_network_security_group` із відкритими портами `22`, `80`, `443`, `azurerm_public_ip`, `azurerm_network_interface`, `azurerm_linux_virtual_machine`) і передає публічну IP-адресу через `outputs.tf`.
- **Ansible (Configuration Management):** виконує ідемпотентне налаштування операційної системи всередині створеної VM поверх SSH — оновлення системних пакетів, налаштування фаєрволу `ufw` (політика `deny incoming`, дозвіл для портів `22`, `80`, `443`), встановлення **Docker Engine** та **Docker Compose plugin**, додавання користувача `azureuser` до групи `docker` і створення структури каталогів проєкту `/opt/studshare/{app,data,nginx}`.

### 2.3. Зберігання стану Terraform (`terraform.tfstate`)
- На етапі розробки та лабораторної верифікації файл стану `terraform.tfstate` зберігається локально в робочій директорії та **обов'язково виключений із Git** через `.gitignore`, оскільки містить метадані ресурсів і мережеві ідентифікатори інфраструктури.
- Для командної роботи в production-середовищі передбачено перехід на віддалений backend (**Azure Blob Storage** із блокуванням стану через State Locking).

## 3. Наслідки
- **Позитивні:** повне розгортання інфраструктури з нуля займає ~2 хвилини (`terraform apply`), повторний запуск Ansible підтверджує ідемпотентність (`changed=0`), а видалення ресурсів (`terraform destroy`) виключає неконтрольоване витрачання хмарного бюджету.
- **Обмеження:** локальний `terraform.tfstate` потребує уважності під час виконання команд із однієї робочої машини та не підходить для одночасного паралельного запуску кількома розробниками без міграції на remote backend.
