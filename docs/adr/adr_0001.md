# ADR-0001: Гібридна архітектура зберігання даних (PostgreSQL + S3 Object Storage)

* **Status:** Accepted (Прийнято)
* **Date:** 2026-11-18
* **Authors:** Команда розробки та DevOps проєкту StudShare

---

## Context (Контекст і проблема)
Студентський портал **StudShare** працює з двома принципово різними типами даних:
1. **Структуровані метадані:** профілі студентів, ієрархія факультетів/кафедр/дисциплін, опис матеріалів, теги, коментарі, голоси (upvotes/downvotes) та історія версій. Ці дані вимагають суворої реляційної цілісності (ACID) та швидкого повнотекстового пошуку.
2. **Неструктуровані бінарні файли:** конспекти у форматі PDF/DOCX, презентації, зображення рукописних лекцій та ZIP-архіви з лабораторними роботами (розмір одного файлу може сягати до $100\text{ МБ}$).

Зберігання великих файлів безпосередньо у реляційній базі даних (як `BLOB` / `BYTEA`) призведе до швидкого розростання БД, деградації продуктивності та складного резервного копіювання. Водночас зберігання файлів у локальній файловій системі сервера порушує принцип *Stateless*-додатків і унеможливлює горизонтальне масштабування контейнерів у Kubernetes.

---

## Decision (Рішення)
Ми ухвалили рішення використати **гібридну схему зберігання даних**:

1. **PostgreSQL 16** використовується як основна реляційна база даних для зберігання всієї бізнес-логіки, зв'язків, користувачів та метаданих файлів (включно з посиланням на об'єкт у сховищі, контрольною сумою SHA-256 та статусом перевірки на віруси).Для швидкого пошуку за назвами предметів і конспектів використовується вбудований механізм PostgreSQL Full-Text Search (`tsvector` та індекси `GIN`).
2. **S3-сумісне об'єктне сховище (MinIO для локальної розробки / AWS S3 або DigitalOcean Spaces для Production)** використовується виключно для зберігання бінарних файлів навчальних матеріалів.
3. **Механізм Pre-signed URLs:** Щоб не перевантажувати Core Backend API прокачуванням гігабайтів трафіку під час сесії, бекенд лише перевіряє права доступу студента та генерує тимчасове криптографічно підписане посилання (*Pre-signed URL*), за яким клієнтський браузер завантажує або скачує файл напряму з S3.

---

## Consequences (Наслідки)

### Позитивні наслідки:
* **Повна Stateless-архітектура бекенду:** Контейнери Core API не зберігають локального стану, що дозволяє Kubernetes миттєво масштабувати їх від $2$ до $10+$ реплік під час пікового навантаження перед іспитами.
* **Економія ресурсів та висока швидкість:** Відвантаження файлів відбувається напряму з об'єктного сховища (з можливістю підключення CDN), не блокуючи потоки Node.js на бекенді.
* **Надійність та бекапи:** База даних PostgreSQL залишається компактною (містить лише текст і метадані), тому її бекапи виконуються за секунди, а об'єктне сховище S3 забезпечує вбудовану реплікацію та версіонування файлів.

### Негативні наслідки та компроміси (Trade-offs):
* **Відсутність розподілених транзакцій між PostgreSQL та S3:** Можлива ситуація («осиротілі файли»), коли користувач завантажив файл у S3, але запис у БД не завершився. *Вирішення:* впровадження статусної моделі запису (`PENDING_UPLOAD` -> `SCANNING` -> `PUBLISHED`) та періодичного фонового CronJob-воркера, який очищує непідтверджені файли в S3, старші за $24$ години.
* **Ускладнення локального середовища розробки:** Розробникам потрібно запускати додатковий сервіс. *Вирішення:* додавання легковагового контейнера **MinIO** у файл `docker-compose.yml`, який повністю емулює S3 API локально.
