# ADR 0004: Вибір CI/CD платформи, стратегія версіонування артефактів та політика Quality Gates

* **Статус:** Accepted
* **Дата:** 2026-11-23
* **Контекст:** Лабораторна робота №3 (Безперервна інтеграція та контроль якості коду для порталу StudShare)

## Контекст
Для реалізації практик Continuous Integration (CI) та принципу «Shift Left» необхідно автоматизувати перевірку стилю коду, виконання модульних тестів, сканування безпеки (DevSecOps), а також збірку й публікацію незмінних Docker-образів у реєстр контейнерів перед злиттям змін в основну гілку `main`.

## Рішення
1. **CI/CD платформа та реєстр контейнерів — GitHub Actions + GitHub Container Registry (GHCR):**
   * Обрано нативну інтеграцію з репозиторієм на GitHub без потреби в підтримці окремого CI-сервера.
   * Для авторизації при публікації образів у `ghcr.io` використовується вбудований токен `${{ secrets.GITHUB_TOKEN }}` із мінімально необхідними правами (`packages: write`).
2. **Стратегія розгалуження — GitHub Flow:**
   * Гілка `main` залишається стабільною та захищеною (Branch Protection Rules: заборона прямих пушів, обов'язкове проходження CI Status Checks та схвалення Pull Request).
   * Усі зміни розробляються у короткоживучих feature-гілках (`feat/*`, `fix/*`) і потрапляють у `main` лише через Pull Request.
3. **Політика Quality Gates (принцип Fail Fast):**
   * **Linting Stage:** перевірка TypeScript/React коду через ESLint та перевірка `Dockerfile` обох сервісів утилітою `hadolint`.
   * **Testing Stage:** запуск ізольованих модульних тестів Backend API (`node --test`) та перевірка успішної збірки Frontend (`vite build`).
   * **Security Stage (DevSecOps):** сканування файлової системи проєкту та зібраних Docker-образів утилітою **Trivy** на відомі CVE-вразливості (виправлені критичні вразливості блокують пайплайн).
   * Етап збірки та публікації артефактів запускається виключно після успішного проходження всіх попередніх перевірок.
4. **Стратегія версіонування артефактів (Build Once, Deploy Anywhere):**
   * Відмова від покладання виключно на мутабельний тег `:latest`.
   * Кожному Docker-образу присвоюється незмінний тег із прив'язкою до короткого хешу коміту `sha-<7-символів>` (наприклад, `ghcr.io/dmitro9/devops-backend:sha-7c27820`), а також семантичні теги `vX.Y.Z` при створенні Git-тегів релізів.

## Розглянуті альтернативи
* **GitLab CI/CD:** потужна платформа з вбудованим реєстром, проте потребує міграції репозиторію з GitHub.
* **Jenkins:** забезпечує високу гнучкість, але вимагає розгортання та адміністрування власного сервера-агента, що надлишково для поточного етапу проєкту.
* **Docker Hub:** популярний публічний реєстр, але потребує створення та ручного керування окремими токенами доступу (`DOCKERHUB_TOKEN`), а також має жорсткіші ліміти на `docker pull` у безкоштовному тарифі порівняно з GHCR.

## Наслідки
### Позитивні
* Повна автоматизація перевірок якості та безпеки на кожному Pull Request і коміті в `main`.
* Гарантована відтворюваність розгортань і можливість швидкого відкату (Rollback) на конкретний `sha-*` образ.
* Прискорення виконання пайплайну завдяки кешуванню залежностей `npm` між запусками.
* Нульові витрати на підтримку інфраструктури CI/CD.

### Негативні та компроміси
* Прив'язка конфігурації пайплайну (`.github/workflows/ci.yml`) до екосистеми GitHub (vendor lock-in).
* Безкоштовний тариф GitHub Actions має місячний ліміт хвилин для приватних репозиторіїв (для нашого публічного репозиторію обмеження відсутні).
